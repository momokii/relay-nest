# Coding Standards

This document is the initial, stack-agnostic baseline. Once the technology stack
is confirmed, replace generic guidance with verified language, framework, tooling,
and repository conventions while retaining the principles that still apply.

## General Principles

- Choose clarity over cleverness; code is read more often than it is written.
- Give each function, file, and module one primary responsibility.
- Prefer explicit behavior over implicit behavior and hidden side effects.
- Fail fast and loudly at the earliest point where an error can be understood.
- Keep public interfaces small, stable, and documented.
- Make invalid states difficult to represent and validate at system boundaries.
- Prefer deterministic, repeatable behavior over convenience that hides state.

## Naming Conventions

- Use `kebab-case` for filenames unless the ecosystem or established project convention requires another form.
- Name functions and methods with descriptive verb-noun pairs such as `getUserById` or `validateInput`.
- Name constants with `UPPER_SNAKE_CASE` when the language convention supports it.
- Prefix boolean values with `is`, `has`, `should`, or `can`.
- Use domain language consistently; do not create synonyms for an established concept.
- Choose names that reveal units, ownership, or lifecycle when those details matter.

## Structure and Change Design

- Follow existing repository structure and patterns before introducing a new one.
- Keep modules cohesive and minimize knowledge of unrelated modules.
- Separate boundary concerns, business logic, persistence, and presentation where the stack supports those layers.
- Avoid premature abstraction; extract a shared abstraction only when its contract is clear.
- Keep configuration outside business logic and make environment-dependent values explicit.
- Record non-obvious design choices in `state/DECISIONS_LOG.md`.

## Error Handling and Observability

- Handle every expected failure path deliberately; never silently swallow errors.
- Preserve the original cause when wrapping or translating an error.
- Log enough structured context to reproduce a failure without logging secrets or personal data.
- Return user-facing errors that are actionable but do not expose stack traces, internal paths, or system details.
- Use consistent error categories and status conventions once the stack establishes them.
- Do not use logging as a substitute for correct error propagation.

## Testing

- Every new feature must include at least one meaningful test.
- Every bug fix must include a regression test that fails before the fix and passes after it.
- Keep tests deterministic, isolated, and independent of real secrets or uncontrolled external services.
- Test success paths, boundary conditions, validation failures, and relevant authorization failures.
- Prefer the narrowest useful test during development, then run the complete suite before completion.
- Make the standard test suite runnable with one documented command once the stack is known.

## Documentation and Comments

- Document every public function, class, module, or endpoint with a description of its contract using the ecosystem's standard format.
- Comment why a non-obvious decision exists, not what obvious syntax does.
- Update user-facing and operational documentation when behavior, configuration, or commands change.
- Keep examples executable or clearly label them as illustrative.

## Formatting and Verification

- Use the repository's formatter, linter, type checker, and test runner once they are established.
- Do not bypass a failing check without documenting the reason and receiving approval when the bypass changes risk.
- Run focused checks after a local change and the full relevant verification set before declaring work complete.
- Keep generated files generated by their owning tool; do not hand-edit them unless the tool explicitly supports it.

## Self-Update

When the stack is confirmed, extend this document with exact language and framework
conventions, formatter and linter configuration paths, test commands, error patterns,
and examples observed in the codebase. Remove generic advice that conflicts with
verified project practice, and record any meaningful convention change in the
decisions log.
